# clew-example-reservations

A worked example of **Code-Anchored Spec-Driven Development (CAS-DD)**: a small Java system whose specifications are anchored into its code as compiler-checked symbols, built increment by increment, ending in a redesign that has to reconcile with everything built before it.

The domain — an equipment reservation engine — is deliberately ordinary.
The point is not the reservation logic; it is what the specifications and their anchors do to the code as it grows and, especially, as it is redesigned.

- The method: **[Code-Anchored Spec-Driven Development](https://ariadne-thread.io/blog/code-anchored-spec-driven-development.html)**
- The tool: **[clew](https://github.com/ariadne-systems/clew)** — the CLI that generates the traceables and reads coverage
- This is a constructed example, not a production system. It exists to be read and run, not deployed.

## Provenance — read this first

Everything in this repository — the specs, the Java, the tests, the ADRs, the commit messages — was written by AI agents.
I set the direction and the tone.
I did **not** review the code, the specs, or the tests myself; the only review in the loop is itself an agent (the per-increment anchoring review).

That is the honest experiment: what does a fully agentic build look like when the method holds every claim the code makes about its specs to the compiler?
You get a history you can *audit* — every `@Realizes` / `@Verifies` link is type-checked, and coverage reports every gap — with no human having vouched for correctness.
The anchors prove the links are sound.
They do **not** prove the code is right, and no human here says it is.

### This history gets rewritten — expect force pushes

**The first commit is the starting kit, and every run branches from it.**
Anything a run needs — the workflow that drives it, the design surface it builds from, the tooling that measures it — has to already exist *in that commit*.
A run cannot pick up something added later: it never sees the commits that come after the one it started from.

That makes the root a living file rather than a historical record, and it is what forces the rewrites.
Improve the starting kit and the improvement belongs at the start, not as a patch commit halfway along.

So a change to the base rewrites the whole repository, and not by rebasing.
Everything after the root was *generated by a run that started from the old root* — carrying those commits forward would leave a history claiming to descend from a starting kit it never saw.
The run is executed again from the new kit and its output replaces what was there.
Only the authored commits survive a rewrite: the starting kit itself, and the STR-6 reveal.
Every checkpoint tag then lands on a new hash.

`main` is force-pushed as a matter of course.
This is a property of the example, not an accident of how it is maintained.

What that means for you:

- **Commit hashes are not stable references.** Cite a tag, not a SHA; and expect the tag to point somewhere new after a re-run.
- **`git pull` will fail after a rewrite.** Use `git fetch --all --tags --force` and reset to `origin/main`, or re-clone.
- **Don't base long-lived work on a clone.** Fork and treat it as a snapshot; there is no upgrade path across a rewrite.

Nothing is lost that you cannot regenerate: the runs are reproducible from the starting kit and the workflow, both of which are in the repository.

## What it demonstrates

**Specifications are compiler-checked claims, not comments.**
Each spec (`SW-001`, `CON-001`, `ENT-001`, …) becomes a generated, typed symbol.
Production code anchors to it with `@Realizes`; tests with `@Verifies`.
Delete or rename a spec and the code that still claims it no longer compiles.

**Coverage is a reverse scan.**
`clew coverage` reads the anchors back and reports, for every spec, whether it is covered (realized *and* verified), realized only, verified only, or unanchored.

**The payoff shows in the redesign.**
The first stories build a coherent single-item system.
The last one — atomic multi-item bookings — cannot be satisfied by adding specs; it forces revising the ones already there.
Watch three things happen: the compiler breaks at every anchor tied to the old single-item shape; coverage flips the revised specs to `none` until they are re-anchored; and a test whose `@Verifies` anchor still compiles green turns out to no longer exercise what it claims — the part only a human or agent review catches.

That last one is the honest edge of the method: the anchor guarantees the link is structurally sound, **not** that the work at either end is correct.

## The stories

| Story | What it adds |
|-------|--------------|
| STR-1 | Set up the workspace |
| STR-2 | Reserve a single item for a time window |
| STR-3 | Tentative holds with expiry |
| STR-4 | Owner-initiated cancellation and release |
| STR-5 | Per-user fair-use quota |
| STR-6 | **Atomic multi-item bookings — the redesign** |

STR-2 through STR-5 quietly assume one item per reservation.
STR-6 removes that assumption, and the git history around it is the real subject of the example.

## Repo layout

```
setup/reservations-cas-dd-demo/   the design surface a run starts from — stories (STR-1..5), specs, ADRs
docs/spec/                        the promoted corpus: architecture.md, specs/, stories/, adr/, schemas/
src/main/java/                    the reservation engine — anchored with @Realizes
src/test/java/                    tests — anchored with @Verifies; ArchUnit boundary tests
.claude/workflows/                the autonomous run that built all of the above
```

The redesign is deliberately kept off the main line so a run stays blind to it: its requirement lives on the `str6-requirement` ref (revealed just-in-time), and its answer key on `str6-answerkey` — neither is present while the single-item system is being built.

An ADR records a decision and its reasoning — the durable *why*.
The ARCH and CON specs derived from it are the atomic, enforced *what* the code anchors to.
They stay few on purpose, and they accrete: `ADR-0001` explains why availability is derived rather than stored (which is what keeps the STR-6 redesign cheap), and the redesign itself adds one — the lock ordering that atomic multi-item bookings force.

## Getting set up

Prerequisites:
- **Node.js and pnpm** — clew is a Node CLI, invoked here as `pnpm run clew …`.
- **JDK 25 and Maven** — the reservation engine is a Maven project.
- **clew** ([github.com/ariadne-systems/clew](https://github.com/ariadne-systems/clew)) — `pnpm install` pulls it in (`@ariadne-thread/clew`) as a dev dependency.

```
pnpm install     # once — installs clew into node_modules
mvn verify       # build the finished single-item system on main; everything is green
```

## Take a look around — you are on `main`

`main` is the finished single-item system: STR-1 through STR-5, green.
Before building anything, read what the method produced — start with the contract it was built under, then the decisions, the specs, and the code that anchors to them.

1. **`.claude/.ai-project-context/`** — the governance the agent worked under; the tour starts here. The **charter** (`001-charta.md`) — *do not invent, preserve traceability, minimize scope* — sits alongside the architecture, coding, testing, and spec conventions (`000`–`006`; `004` and `005` are the stack and testing contracts). Every spec, anchor, and line below was produced within this contract.
2. **`docs/spec/architecture.md`** — the narrative shape of the system: its modules, how they layer, the dependency directions, the nullness and runtime rules. This is the prose the `ARCH` and `CON` specs then pin as enforceable checks (and the `ArchitectureBoundariesTest` runs).
3. **`docs/spec/adr/`** — the Architecture Decision Records: the durable *why* behind that shape (e.g. `ADR-0003`, availability is computed rather than stored; `ADR-0001`, anchors are enforced by the type checker).
4. **`docs/spec/stories/`** — the five stories (`STR-001`…`STR-005`); each states a work item and references the specs it realizes.
5. **`docs/spec/specs/`** — the specs themselves, one decision per file, by lens (`STK`/`SYS`/`SW`/`ARCH`/`NF`/`CON`/`ENT`). These are what the code anchors to. `ENT` is a project lens, not a clew default — and a custom lens has to be declared in **two** places: `.clewrc.json`'s `lenses` array **and** the `Lens` enum in `docs/spec/schemas/spec.schema.yaml` (miss the schema and it fails validation on promote). This seed pre-declares it in both.
6. **`src/main/java/clew/traceables/clew/`** — the code `pnpm run clew spec` *generates* from those specs: the typed traceables (`SwTraceables`, `ConTraceables`, …) and the `@Realizes` / `@Verifies` / `@Concerns` annotations that turn a spec id into a compiler-checked symbol. Its own `README.md` documents the marker form.
7. **A real anchor.** Open `src/main/java/io/example/reservations/services/reservation/DefaultConfirmService.java` — the `confirm(…)` method carries

   ```java
   @RealizesSw(SwTraceables.SW_001_CONFIRM_SERVICE)
   @RealizesCon({ConTraceables.CON_001_NO_DOUBLE_BOOKING, ConTraceables.CON_003_QUOTA_BOUND})
   public Reservation confirm(User user, Item item, TimeWindow window) { … }
   ```

   and its test `src/test/java/io/example/reservations/services/reservation/ConfirmServiceTest.java` carries `@VerifiesSw(SwTraceables.SW_001_CONFIRM_SERVICE)`. Ask clew where a spec lives — it resolves the id to its exact anchor sites:

   ```
   pnpm run clew anchors SW-001
   ```
8. **Read the anchors back** — three views over the whole corpus:

   ```
   pnpm run clew coverage   # per spec: covered / realized-only / verified-only / unanchored
   pnpm run clew scan       # every anchor by spec id with file:line; writes .clew/locations.json
   pnpm run clew check      # integrity gate: no anchor names a missing spec, no spec id hides in a comment
   ```
9. **Break it — prove the anchor is compiler-checked.** Delete a spec, regenerate the traceables, and recompile:

   ```
   rm docs/spec/specs/SW-001-confirm-service.md
   pnpm run clew spec
   mvn compile
   ```

   Compilation fails at every line that still anchors `SW-001` — the drift is caught by the type checker, not by a reviewer. Restore everything with `git checkout .`.

## Build it yourself, or watch it build

You have seen the result; the git history is how it got there — `git log --oneline` walks the whole construction, each increment a draft commit then an implement commit.
Below are three **independent** ways in — **pick one**; they are alternatives, not sequential steps, ordered here from hands-off to hands-on.

> **This is a demo, not a real project.**
> In real CAS-DD the agent *derives* each story's specs from the code and its anchors — nothing is pre-written.
> Here the stories and specs are **pre-authored and fixed** in `setup/` (the design surface in this repo's initial commit); each run *reproduces* them rather than inventing them.
> That is the one deliberate deviation from the method — and what makes the build deterministically reproducible: the same corpus and the same code every run, not whatever an agent might derive on a given day.
> Everything else — promote, implement, anchor, coverage — is the real loop.
> How the seed is constructed: [`setup/reservations-cas-dd-demo/README.md`](setup/reservations-cas-dd-demo/README.md).

> **Start each run on a branch, from the bare surface.**
> These checkpoints are git *tags*, so a bare `git checkout initial-setup` lands you on a detached HEAD — a run's commits would then belong to no branch, and `main` would be left behind. Branch off the tag instead (the paths below do this).
> A run also builds into the working tree — the corpus under `docs/spec/`, the engine under `src/` — so it must begin pristine; a fresh branch off `initial-setup` already is.
> To re-run after an attempt, reset your branch back and clean:
> ```
> git reset --hard initial-setup && git clean -fd    # keeps node_modules/ and .claude/workflows/
> ```

**Pick your path** (rough time):
- **A — Run it (Claude Code)** — hands-off; the workflow builds all six stories for you. **≈ 2 h.**
- **B — Build it yourself** — hands-on; work the CAS-DD loop by hand, story by story. **≈ 2 h**, more if you review as you go.
- **C — Just the redesign** — start from the green single-item system and do only the STR-6 redesign. **≈ 30–60 min** (one increment).

### A — Run it (Claude Code)

```
git checkout -b run initial-setup
```

Open the repo in Claude Code and launch the workflow by typing its name as a slash command:

```
/reservations-cas-dd-full-run
```

Approve it when prompted; it then runs in the background — scaffolding clew and building all six stories autonomously, keeping the redesign blind (the same run that produced this repo).
Watch live progress with `/workflows` (that command only *watches* a running workflow — it does not launch one).

> It spawns many subagents and runs on the order of **50M tokens**, the bulk of them prompt-cache reads, so plan for real cost.

### B — Build it yourself

```
git checkout -b run initial-setup
```

Point your agent at the repo and begin with clew's scaffolding:

```
pnpm run clew setup
```

That writes clew's config, skills, and governance — start a fresh agent session so it picks them up. Then tell it, in plain language:

> **Set up the project.**

It runs clew's setup skill and works the **STR-1 setup story**, standing up the Maven workspace to the architecture in `setup/`: the module layout, the build, the tests, the ArchUnit boundary rules.
**Expect this to take a while** — it installs, builds, and re-runs the suite to reach a green skeleton before a single domain story, so you approve a steady stream of commands as it goes.
From there, work the domain stories one at a time — **STR-2 through STR-6**.
Each is the same three-prompt loop; for STR-2 (reserve a single item):

1. **Draft** — *"Draft STR-2 and its specs, reproducing them from the seed."*
2. **Promote** — *"Promote STR-2."*
3. **Implement + anchor** — *"Implement STR-2 and anchor it."*

The agent reproduces the fixed story and specs from `setup/`, binds their ids into the corpus, then writes the code and tests — anchored with `@Realizes` / `@Verifies` — and confirms each spec reads Covered.
Repeat for STR-3, STR-4, STR-5 — then STR-6, the redesign, which you *derive* rather than reproduce (path C covers exactly that step).

### C — Just the redesign

```
git checkout -b redesign str6-requirement
```

The single-item system, all green (STR-1 through STR-5), with the STR-6 redesign requirement revealed (`setup/reservations-cas-dd-demo/stories/STR-6-*.md`).
Unlike the earlier stories, STR-6's specs are **not** in the seed — you derive the redesign from the plain requirement. The same three-prompt loop:

1. **Draft** — *"Draft STR-6 from its requirement — derive the new specs it needs and the revisions to the existing ones."*
2. **Promote** — *"Promote STR-6."*
3. **Implement + anchor** — *"Implement STR-6 and anchor it."*

Watch it land: the compiler breaks at every anchor on the old one-item shape, coverage flips the revised specs to `none` until they are re-anchored, and a green-but-stale `@Verifies` test can slip through — the one only review catches.
Compare your result against `full-run` (the reference solution).

## Why there are two arms

The claim this example makes is that anchoring intent into code changes what it costs to work on a system, and how well that work goes.
A single run cannot show that: you get numbers with nothing to compare them against.

So the same six stories are built a second way — from the stories and the design surface alone, with no specification corpus, no anchors, and no coverage over specs.
Both runs use identical measurement tooling: it is the repository's first commit, shared by both lines, so the token, time and outcome figures on either side are produced by the same definitions.

The control arm's inputs, and the reasoning behind every edit made to produce them, are in [`docs/baseline-input-set.md`](docs/baseline-input-set.md).
Its line shares only that tooling commit and the common project files with this one, and diverges before either method appears — the specification corpus is not reachable from it, so a run there cannot read the answers this line was built from.

Run either arm the same way:

```bash
node .claude/workflows/metrics/new-run.mjs --arm cas-dd   --base initial-setup
node .claude/workflows/metrics/new-run.mjs --arm baseline --base baseline-setup
```

Each prepares an isolated worktree at the chosen starting kit and prints the command that runs it.
Every run writes its own report; you can read two of them side by side, or use `compare-runs.mjs`.

## What this example does not claim

It does not show that the code is *correct* — only that the code's claims about which specs it realizes and verifies are kept honest by the build.
It does not show that CAS-DD is worth its cost on a weekend script; it is deliberately the kind of long-lived, refactor-heavy system where the method pays off.
And it is one system built with the method, by design a favourable case — the real test is your codebase, not this one.
